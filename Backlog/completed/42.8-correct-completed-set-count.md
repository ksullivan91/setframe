# Story 42.8 — Fix Incorrect Completed Set Count

## Original Product Feedback

> Okay, a bit more on 42.
>
> Where it says sets completed, the number is wrong. I had planned 5, completed 6, but it says I completed 4. I made sure all of it was filled out and saved. So not sure what the bug is there.

## Product / UX Response

This looks like a separate data-integrity bug inside Story 42 rather than a visual-only issue.

The completed exercise card is reporting `4 sets completed`, even though the session actually contains 6 completed sets and the plan was 5. That means the count shown in the card is almost certainly being derived from the wrong source or filtered by the wrong rule.

The completed count should represent actual completed session sets for that exercise in the current workout session. It should not be capped to the planned set count, inferred from template sets, based on only working sets, or accidentally omit dynamically added/backoff/warmup sets.

Because the screenshots show Set 6 exists and is fully populated, Claude should trace the count all the way from persisted session sets through the completion selector into the completed-card summary. This should be fixed before any more completion-card polish because the summary has to be trustworthy.

---

## User Story

As a user reviewing an exercise during an active or completed workout, I want the completed-set count to reflect the sets I actually completed in that session, so that the exercise summary is trustworthy even when I perform more or fewer sets than originally planned.

## Screenshot / Gym-Test Evidence

The latest gym test shows:

- **Barbell Romanian Deadlift**
- Planned prescription: **5 × 8**
- User actually completed **6 sets**
- Set 6 is visible in the expanded exercise and contains valid saved data
- The collapsed completed card incorrectly reports **“4 sets completed”**

This is not a wording issue. The displayed count is factually wrong.

## Problem Statement

The completed-card summary is deriving `sets completed` from an incorrect source or rule.

Potential failure modes Claude must investigate rather than assume:

1. counting template/planned sets instead of current-session sets
2. counting only a subset of set types
3. excluding dynamically added sets
4. excluding warmup/backoff sets unintentionally
5. relying on stale cached exercise state
6. calculating completion before the final set mutation resolves
7. counting only sets present when the workout was initially instantiated
8. using a selector that caps actual sets at planned-set length
9. filtering by an incorrect `isComplete` / `isSaved` condition
10. optimistic state updating the cards and detailed-set collection independently
11. deriving card count from `plannedSetCount - remainingSets`
12. reading a stale query cache after adding/saving extra sets

The implementation must identify the real source of truth and remove competing calculations.

## Product Intent

There are two separate quantities:

```text
planned sets
actual completed sets
```

They are allowed to differ.

Examples:

```text
Planned: 5 × 8
Actual: 6 completed sets
```

```text
Planned: 5 × 8
Actual: 4 completed sets
```

The UI should never silently force these numbers to match.

### Correct collapsed-card behavior

For this gym-test example:

```text
Planned: 5 × 8
6 sets completed
```

The planned pill communicates the original intent.

The completed-set label communicates what actually happened.

## Canonical Counting Rule

`completedSetCount` must be derived from **current workout-session set records for this exercise** that satisfy the canonical saved/completed-set rule.

Conceptually:

```ts
completedSetCount =
  sessionExercise.sets.filter(isActuallyCompletedSet).length
```

Do not derive the count from:

```ts
plannedSetCount
template.sets.length
Math.min(actual, planned)
workingSetsOnly
visibleSets.length
initialSessionSets.length
```

unless a product rule explicitly requires one of those, which it currently does not.

## Required Investigation

1. workout template prescription

4. dynamically added sets
5. set save mutation
6. optimistic cache update

Do not fix this by adding `+ 2`, using planned-set length, or changing display logic only.

## Set-Type Rules

Unless the product domain explicitly says otherwise, a completed set should count regardless of whether it is:

- warmup
- working
- backoff
- drop set
- dynamically added set
- any other valid set type

The count represents completed session sets, not only working sets.

If current product logic intentionally excludes any set types from this count, that rule must be surfaced for product review before implementation.

## Acceptance Criteria

- [ ] Planned set count and actual completed-set count are treated as independent values.
- [ ] A workout planned for 5 sets can correctly display **6 sets completed**.
- [ ] A workout planned for 5 sets can correctly display **4 sets completed**.
- [ ] Dynamically added sets are included once they satisfy the canonical completed-set rule.
- [ ] Saved warmup/backoff sets are not silently dropped from the count unless there is an explicitly approved product rule.
- [ ] The card count updates optimistically when an additional set is successfully logged.
- [ ] The count reconciles correctly with the persisted server response.
- [ ] Refreshing the page preserves the same completed-set count.
- [ ] Expanding and collapsing the exercise does not change the count.
- [ ] Completing the workout does not change the historical count.
- [ ] Editing or deleting a completed set recalculates the count correctly.
- [ ] A failed set save does not permanently increment the persisted completed-set count.
- [ ] The same canonical selector/domain function is used anywhere Setframe displays completed-set totals for an exercise.
- [ ] No separate component-local completion-count formula remains.

## Important Distinction: Count vs Exercise Completion

Do not conflate:

```text
completedSetCount
```

with:

```text
isExerciseComplete
```

For example:

```text
planned = 5
completed = 6
isExerciseComplete = true
```

and:

```text
planned = 5
completed = 4
isExerciseComplete = false
```

may both be valid.

Story 42's previous bugs came from collapsing multiple concepts into one boolean/count. Keep them separate.

## Claude Steering Document

### Do not start with the component

The screenshot is where the bug is visible, but the component may not be where the bug originates.

Trace the data.

### First question to answer

Why does this exercise have 6 valid visible sets while the summary says 4?

Write down the exact calculation that currently produces `4`.

### Then identify the correct source of truth

There should be one canonical function such as:

```ts
getCompletedSessionSets(sessionExercise)
```

or:

```ts
selectCompletedSetCount(sessionExerciseId)
```

Naming is illustrative.

### Check optimistic mutations

Because Story 42 is introducing optimistic logging, verify that:

- add-set mutation updates the same normalized session-exercise cache
- save-set mutation updates the same collection
- card summary reads from that collection
- detailed editor reads from that collection

Do not allow the detailed editor and collapsed summary to maintain separate copies of the exercise.

### Check stale initial arrays

Pay special attention to patterns like:

```ts
const expectedSets = exercise.sets.slice(0, plannedSetCount)
```

or state initialized once:

```ts
const [sets, setSets] = useState(initialSets)
```

that is never reconciled after dynamic additions.

### Check filters

Search for filters involving:

```text
working
warmup
backoff
completed
saved
actual
status
planned
```

The number `4` strongly suggests at least one valid set is being excluded by a rule.

### Do not patch the symptom

Forbidden fixes include:

```ts
Math.max(plannedCount, completedCount)
completedCount + dynamicallyAddedCount
plannedCount
```

unless they are truly the domain model, which they should not be here.

The card should simply report the truth contained in the session data.
